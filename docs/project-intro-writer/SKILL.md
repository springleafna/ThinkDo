# 项目介绍文档生成 Skill

## 目标

根据项目现有资料，输出一份面向业务、产品、汇报或需求沟通场景的中文 Markdown 文档。

始终聚焦以下内容：

- 项目是做什么的
- 解决了什么问题
- 面向哪些用户
- 具备哪些核心功能
- 需求如何拆解
- 功能之间如何形成完整业务闭环

不要把重点放在技术实现上，不要把文档写成开发设计说明。

## 输出原则

- 只写中文
- 使用业务语言、产品语言、用户语言
- 优先解释“为什么需要”“解决什么问题”“用户如何使用”
- 可以概括模块能力，但不要写类名、包名、接口路径、表名、字段名、脚本名
- 不写代码块
- 不展开技术栈、框架选型、底层实现、部署细节、性能调优方案
- 如果资料不足，先基于现有信息做保守推断，并在文档中明确“以下内容基于现有资料整理”

## 信息收集顺序

生成文档前，优先从以下材料提取业务信息：

1. `docs` 目录下的功能清单、产品说明、需求文档、原型说明
2. 项目中已有的中文提示词、文案、菜单命名、模块命名
3. 项目目录名、模块名、领域对象命名中透露出的业务边界
4. 测试名称、数据库注释、接口语义中可以直接反映业务功能的内容

提取信息时要做“业务化转述”：

- 把技术名称转成业务能力
- 把模块职责转成用户可感知的功能
- 把内部流程转成业务流程

例如：

- “知识库文档上传、切片、检索”应转述为“支持知识资料沉淀、管理与问答调用”
- “会话管理、流式输出”应转述为“支持实时对话与历史会话管理”
- “计划分类、执行清单、步骤管理”应转述为“支持计划拆解、日程执行与过程跟踪”

## 禁止内容

文档中不要出现以下内容：

- 代码实现说明
- 技术架构图解
- 框架、中间件、数据库选型分析
- 接口地址、请求参数、返回结构
- 数据表设计、字段设计、索引设计
- 类、方法、包、脚本、配置项名称
- 开发排期、代码改造细节、重构说明

如果用户明确要求“项目介绍”“需求分析”“功能说明”“产品概述”，默认忽略代码层信息。

## 默认写作流程

### 第一步：判断文档目标

先判断文档属于哪一类：

- 项目整体介绍
- 产品功能说明
- 需求分析文档
- 立项/汇报材料
- 模块能力概述

如果用户没有明确指定，默认按“项目整体介绍 + 功能介绍 + 需求分析”组合输出。

### 第二步：提炼业务主线

在动笔前先明确以下五个问题：

- 项目的核心定位是什么
- 目标用户是谁
- 用户当前痛点是什么
- 系统提供了哪些能力来解决问题
- 最终形成了怎样的使用闭环

如果项目是多模块系统，不按技术模块堆叠介绍，而是按用户场景或业务链路组织内容。

### 第三步：组织文档结构

默认采用以下结构，可根据项目规模适当增减章节。

## 标准输出结构

### 1. 项目简介

说明项目定位、核心目标和一句话价值概括。

建议回答：

- 这是一个什么项目
- 服务于什么场景
- 核心价值是什么

### 2. 建设背景

说明项目为什么要做，聚焦实际业务痛点，例如：

- 信息分散，难以沉淀
- 任务执行缺少闭环
- 笔记、计划、知识资料彼此割裂
- 用户需要更高效的智能辅助能力

### 3. 目标用户

说明主要服务对象，并按角色描述诉求，例如：

- 个人用户
- 团队协作成员
- 知识管理者
- 日常任务执行者

### 4. 核心功能介绍

按业务能力分组介绍，不按技术模块逐个罗列。每项功能建议包含：

- 功能名称
- 功能目标
- 解决的问题
- 用户可获得的价值

推荐分组方式：

- 智能问答与辅助
- 知识沉淀与检索
- 笔记记录与整理
- 计划制定与执行
- 日常管理与个人效率提升

### 5. 需求分析

需求分析部分优先从业务需求出发，建议拆成以下三层：

#### 5.1 用户需求

描述用户想完成什么事，而不是系统怎么实现。

例如：

- 用户希望快速记录信息，并能后续检索和复用
- 用户希望把计划拆解成可执行步骤，并跟踪进度
- 用户希望基于已有知识进行问答，减少重复查找成本

#### 5.2 功能需求

把用户需求映射为系统能力，说明系统需要提供哪些功能来支撑。

写法要求：

- 一条需求对应一类能力
- 用“支持……”“提供……”“允许用户……”表述
- 不写接口行为，不写实现逻辑

#### 5.3 业务价值

说明这些需求落地后带来的结果，例如：

- 提升知识复用效率
- 降低任务遗漏概率
- 提升个人规划与执行效率
- 增强智能辅助体验

### 6. 典型使用场景

至少给出 3 个贴近真实业务的场景，用“某类用户 + 某种目标 + 使用路径 + 结果”描述。

### 7. 功能边界与说明

说明项目当前聚焦哪些能力，不延伸描述未实现的技术细节。可以写：

- 当前重点支持的范围
- 暂不覆盖的场景
- 后续可扩展方向

### 8. 总结

用一段简洁的话概括项目整体价值、适用场景和建设意义。

## 写作要求

- 标题清晰，层次分明
- 段落简洁，避免空话
- 同时兼顾“项目说明”和“需求说明”两种阅读视角
- 优先体现业务闭环，不要只做模块清单堆砌
- 如果项目本身带有 AI 能力，重点描述用户价值，不要描述模型接入方式
- 如果资料只能支持部分结论，不要编造细节，可用“当前资料显示”“从现有功能看”这类表达控制语气

## 默认输出模板

可直接按以下骨架生成：

```markdown
# {项目名称}项目介绍

## 一、项目简介

## 二、建设背景

## 三、目标用户

## 四、核心功能介绍

## 五、需求分析
### 5.1 用户需求
### 5.2 功能需求
### 5.3 业务价值

## 六、典型使用场景

## 七、功能边界与后续方向

## 八、总结
```

如果用户要求更正式的文风，可将一级标题改为“项目概述、需求分析、功能设计、应用价值”等更正式表述。

## 质量检查清单

输出前逐项检查：

- 是否通篇使用中文
- 是否聚焦需求、功能、场景、价值
- 是否出现代码、接口、表结构、技术选型等内容
- 是否解释了项目存在的必要性
- 是否说明了目标用户和实际场景
- 是否把功能和需求建立了对应关系
- 是否避免把文档写成技术说明书

## 示例触发语

以下请求应触发本 skill：

- 帮我写一份项目介绍
- 根据当前项目整理功能说明文档
- 输出一份中文需求分析
- 帮我写项目概述和功能介绍，不要写代码实现
- 结合现有项目资料生成产品说明文档

## 执行偏好

- 优先输出完整 Markdown 文档
- 默认文件放在 `docs` 目录
- 默认文件名可使用 `项目介绍.md`、`需求分析.md`、`产品功能说明.md`
- 如果用户没有指定篇幅，默认输出中等详细程度，保证内容完整但不过度冗长
